# 中文 AI 简历产品：模块化开发计划与 Feature PR 流程

> 版本：1.0，2026-10-12。首发：中国大陆；当前没有收款渠道。
> 本文件是功能范围、依赖和验收的事实来源；实际状态以 [功能跟踪表](chinese-ai-resume-feature-tracker.md) 和 GitHub PR 为准。
> 产品、价格、支付申请与公开发布要求见 [上线方案](chinese-ai-resume-vip-launch.plan.md)。执行规则见根目录 [AGENTS.md](../../AGENTS.md)。

## 1. 交付原则

- 保留现有 React/Hono/oRPC/Drizzle/PDF 架构；每个功能尽量复用既有能力。
- 每个功能一个固定 ID、一个 feature 分支、一个 PR，目标始终是 `dev`。
- 分支名为 `codex/feature/fNNN-short-name`。在功能开始时从最新 `origin/dev` 创建，不提前建立整个分支池。
- 依赖只认已经合并到 `dev` 的 PR。未合并的代码不作为下一个功能的起点。
- 测试、翻译、迁移、文档、状态更新属于对应功能；最终 E2E 功能负责跨模块验收，不能替代各功能自己的测试。
- 开发完成、PR 已创建、PR 已合并、产品已上线是四种状态，分别记录。
- 不自动合并，不直接提交 `main`/`dev`，不因代码完成自动部署或开启真实收款。

仓库：`origin = ryan-deng98/reactive-resume`。`upstream` 仅作原项目参考。`dev` 从已核对的 `main` 提交 `4891443812b497acfc6cdb0572840f05bfe674b4` 初始化；以后通过 PR 集成。

## 2. 范围、时间与检查类型

全计划共 **11 个模块、47 个功能（F000–F046）**。其中 F000 是本次流程/计划交付，F001–F033 是首发工程范围；F034–F042 是求职扩展；F043–F046 是商业增长，后两阶段按真实数据决定是否实施。

早期 12–15 工作日估计针对粗粒度候选版本。按本次要求增加逐功能分支、独立 PR、依赖合并和验证，**首发按 20–30 个工作日工程预算安排**，前提是 1 名熟悉技术栈的开发者、及时的人工评审、既有基线无重大故障。等待评审、主体/支付/网站/AI 手续时间另计；首次基线验收后重新估时。

| 检查代号 | 必要内容                                                                      |
| -------- | ----------------------------------------------------------------------------- |
| D        | 文档格式、diff/空白、链接与路径、ID/分支/依赖一致性                           |
| W        | Web typecheck、lint/format，相关 UI 行为或人工验收；关键流程再做浏览器检查    |
| A        | API/相关包 typecheck、业务单测；鉴权、额度、订单等还需真实隔离 DB 集成测试    |
| DB       | Drizzle 生成迁移、SQL 审查、空库/已有测试库迁移、约束与事务测试、数据回滚策略 |
| P        | 支付签名/通知/查单/退款模拟与 DB 测试；禁止以真实支付代替自动测试             |
| R        | 生产构建、受影响 PDF/DOCX 渲染验证、中文字体/分页/文本读取与适用标识验证      |
| E        | 构建后的隔离环境 Playwright E2E、关键失败/恢复场景与上线检查                  |

所有代码 PR 还须执行 AGENTS.md 规定的 lint/format；共享契约/导出/导入变更检查 boundaries。新增用户文案使用 Lingui；公共 API 与职业功能文档随功能更新。下表检查代号说明专项验证，不免除通用检查。

## 15. Feature session 操作清单

### 开始

1. 读 AGENTS.md、本计划和跟踪表，确认用户授权的功能。
2. 查看当前分支、工作区、GitHub PR/checks、所有依赖是否合并。
3. 拉取 `origin`；有未提交工作时先识别归属，不自动 stash/reset/clean。
4. 当前功能已有分支则继续；否则从最新 `origin/dev` 建 tracker 指定分支。
5. 更新状态 `in_progress`、当前范围和预期检查，再开始代码。

示例（仅在工作区适合切分支、依赖已合并时）：

```sh
git fetch origin
git switch -c codex/feature/f010-experience-rewrite origin/dev
```

### 实现与验收

- 先确认接口、数据和错误契约，再实现功能与对应测试。
- 调整 DB/契约/环境时同步消费者、迁移/文档/环境白名单，使用所属包出口。
- 跑适用检查；更新 dev 时发生冲突或代码变化，重跑受影响验证。
- 只暂存功能文件与必要跟踪记录；检查 staged diff，不用 `git add .` 携带本地环境或无关工作。
- 提交使用 Conventional Commits，例如 `feat(ai): add evidence-preserving Chinese rewrites`。

### PR 与交接

```sh
git push -u origin codex/feature/f010-experience-rewrite
gh pr create --repo ryan-deng98/reactive-resume --base dev --head codex/feature/f010-experience-rewrite --title "feat(ai): add Chinese experience rewrites" --body-file /private/tmp/f010-pr.md
```

多行正文先写文件，避免 shell 转义改坏内容。若验证/环境被阻塞，增加 `--draft`，列出未完成项。完成后记录/提交 PR URL 与检查证据，附加 PR 到当前 chat，并查看最新 head 的 CI；本步骤不执行 merge。

依赖功能只有 GitHub 确认合并到 dev 才可启动。评审修改继续同一个分支/PR，不另开重复 PR。

## 16. PR 模板与 Definition of Done

每份 PR 正文至少包含：

```markdown
Feature: F010 — 中文单段经历润色
Base: dev
Dependencies: F004, F009 (merged)

Problem and behavior:

- Describe the user trigger and final behavior, including failure handling.

Scope:

- List the feature behavior and necessary supporting changes.

Validation:

- Exact commands/checks run and their results.
- Manual/browser evidence where applicable.
- Skipped or failed checks with reasons; no claims of passes without evidence.

Data and rollout:

- Migrations, feature flags, rollback implications, and external activation gates.

Remaining:

- Any blockers or reviewer action needed.
```

准备评审需要功能验收、对应测试、本地检查和文档完成。完成集成还需要 required CI 通过、人工审查完成、用户授权的 merge 以及 GitHub 确认已并入 dev；CI pending/failed 单独记录。公开上线还需要以下外部门槛。
